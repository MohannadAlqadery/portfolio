This is the note I actually wanted to write after eJPTv2. The exam teaches you the attacker's loop: discover, enumerate, get in, escalate, move. Sitting on the other side of that in a SOC, the question is simpler: what did each of those steps leave in the logs, and how do I find it before it turns into a bad day?

Everything below is detection. The queries are starting points: run them, look at what normal looks like in your environment, and only then pick thresholds.

## 1. Host discovery and port scans

From the network, a scan is a fan-out: one source, many destinations or many ports, very little data. Firewall logs in Sentinel (`CommonSecurityLog`) make it easy to see:

```kql
CommonSecurityLog
| where TimeGenerated > ago(1h)
| summarize Ports = dcount(DestinationPort), Hosts = dcount(DestinationIP), Events = count()
    by SourceIP, bin(TimeGenerated, 5m)
| where Ports > 50 or Hosts > 20
| order by Ports desc
```

From the endpoint side, Defender sees the connection attempts too. This catches an internal machine doing the scanning, which is far more interesting than an external one:

```kql
DeviceNetworkEvents
| where Timestamp > ago(1h)
| where ActionType in ("ConnectionFailed", "ConnectionAttempt")
| where ipv4_is_private(RemoteIP)
| summarize Targets = dcount(RemoteIP), Ports = dcount(RemotePort)
    by DeviceName, InitiatingProcessFileName, bin(Timestamp, 5m)
| where Targets > 20 or Ports > 50
```

`InitiatingProcessFileName` usually answers the first question for you. A known scanner run by the IT team is a ticket. `powershell.exe` or an unknown binary is an incident.

## 2. Web directory brute forcing

Wordlist scanning is loud in web logs: lots of 404s, from one client, in a short time, often with a tool's default user agent. In Splunk with standard Apache access logs:

```spl
index=web sourcetype=access_combined status=404
| bin _time span=1m
| stats count AS not_found dc(uri_path) AS paths values(useragent) AS agents BY _time, clientip
| where not_found > 100
| sort - not_found
```

The follow-up is what matters: did any request from that client get a `200` on something it shouldn't have, like a backup file, an admin page or a config? Swap `status=404` for `status=200` and filter to that `clientip`.

## 3. Password guessing

### Windows

Event 4625 is a failed logon. The logon type tells you how: 3 is network (SMB, for example), 10 is remote desktop.

```kql
SecurityEvent
| where TimeGenerated > ago(1h)
| where EventID == 4625
| summarize Failures = count(), Accounts = dcount(TargetUserName)
    by IpAddress, LogonType, bin(TimeGenerated, 10m)
| where Failures > 20
```

Then the query that actually matters: failures followed by a success from the same source.

```kql
let failures = SecurityEvent
    | where TimeGenerated > ago(1h) and EventID == 4625
    | summarize Failures = count() by IpAddress, TargetUserName
    | where Failures > 20;
SecurityEvent
| where TimeGenerated > ago(1h) and EventID == 4624
| join kind=inner failures on IpAddress, TargetUserName
| project TimeGenerated, TargetUserName, IpAddress, LogonType, Failures
```

If this returns a row, I'm not triaging an alert any more, I'm investigating a compromised account.

### Linux

SSH failures land in `auth.log` (or the journal), and in Sentinel's `Syslog` table if it's forwarded:

```kql
Syslog
| where TimeGenerated > ago(1h)
| where ProcessName == "sshd" and SyslogMessage has "Failed password"
| extend SourceIP = extract(@"from (\d+\.\d+\.\d+\.\d+)", 1, SyslogMessage)
| summarize Attempts = count() by HostName, SourceIP
| where Attempts > 15
```

On the box itself, the same thing in a pinch:

```bash
grep "Failed password" /var/log/auth.log | awk '{print $(NF-3)}' | sort | uniq -c | sort -rn | head
grep "Accepted" /var/log/auth.log | tail -20
```

## 4. Exploiting a service

Service exploitation on Windows tends to leave one of two traces: a service that wasn't there before, or a system process spawning something it shouldn't.

New services are event 7045 in the System log:

```kql
Event
| where TimeGenerated > ago(1d)
| where EventLog == "System" and EventID == 7045
| project TimeGenerated, Computer, RenderedDescription
```

And unusual children of core system processes, from Defender:

```kql
DeviceProcessEvents
| where Timestamp > ago(1d)
| where InitiatingProcessFileName in~ ("services.exe", "spoolsv.exe", "lsass.exe", "wmiprvse.exe")
| where FileName in~ ("cmd.exe", "powershell.exe", "rundll32.exe", "mshta.exe")
| project Timestamp, DeviceName, AccountName, InitiatingProcessFileName, FileName, ProcessCommandLine
```

`services.exe` starting `cmd.exe` is exactly what remote service-based execution looks like. Sometimes it's an admin tool. Always worth a look.

## 5. Post-exploitation recon

Attackers who've just landed all ask the same questions: who am I, what is this machine, what's on the network? The commands are harmless individually. The cluster is the signal:

```kql
DeviceProcessEvents
| where Timestamp > ago(1d)
| where FileName in~ ("whoami.exe", "systeminfo.exe", "ipconfig.exe", "net.exe", "net1.exe", "nltest.exe", "quser.exe")
| summarize Commands = make_set(ProcessCommandLine, 20), Count = count()
    by DeviceName, AccountName, bin(Timestamp, 10m)
| where Count >= 4
```

Read the `Commands` set as a story. `net group "domain admins" /domain` in there turns a curious user into a priority.

## 6. Privilege escalation

Signals I'd watch:

- **Windows event 4672** (special privileges assigned) for an account that has never had them before. Pair it with a `leftanti` join against the last 30 days to find first-time admins.
- **Linux `sudo` entries** in `auth.log` for users who don't normally use sudo, and `sudo -l` showing up at all from a service account.
- **New members of privileged groups**: events 4728, 4732 and 4756.

```kql
SecurityEvent
| where TimeGenerated > ago(7d)
| where EventID in (4728, 4732, 4756)
| project TimeGenerated, Computer, GroupName = TargetUserName, MemberAdded = MemberName, ChangedBy = SubjectUserName
```

## 7. Pivoting and lateral movement

This is the one I care about most, because it's how a single bad laptop becomes an incident report. An internal host connecting to many other internal hosts on admin ports is rarely innocent:

```kql
DeviceNetworkEvents
| where Timestamp > ago(1d)
| where RemotePort in (22, 135, 445, 3389, 5985, 5986)
| where ipv4_is_private(RemoteIP)
| summarize Targets = dcount(RemoteIP), Ports = make_set(RemotePort)
    by DeviceName, InitiatingProcessFileName, bin(Timestamp, 10m)
| where Targets > 10
```

Remote logons tell the other half of the story. Type 3 and type 10 logons onto a server from a workstation that's never connected to it before are worth a second look.

## How I'd use these on shift

- **Correlate, don't stack.** One scan alert, one brute-force alert and one recon alert on the same host within an hour is one incident, not three tickets.
- **Ask what came next.** Every query above has an obvious follow-up: did the scan find something, did the guessing succeed, did the recon lead to movement?
- **Tune with evidence.** If the IT team's scanner trips the rule every Tuesday, put it in a watchlist with a note explaining why. Don't just raise the threshold until the noise goes away.
- **Write it down.** Whatever you find, the case notes should let the next person repeat your queries without asking you.
