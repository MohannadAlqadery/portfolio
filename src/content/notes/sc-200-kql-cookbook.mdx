This is less a study note and more the scratchpad I'd want open in a second tab. None of these are clever. They're the shapes that come up again and again, written so I can change two lines and reuse them.

A quick warning first: copy the idea, not the thresholds. A "more than 20 failures" that's perfect for one tenant is noise in another. Run the query without the final `where`, look at the numbers, then pick a line.

## Start every query the same way

Time first, then the cheapest filters, then the expensive work:

```kql
SigninLogs
| where TimeGenerated > ago(1d)           // 1. time
| where ResultType != "0"                 // 2. cheap filter
| where AppDisplayName has "Azure Portal" // 3. narrower filter
| summarize Failures = count() by UserPrincipalName, IPAddress
| order by Failures desc
```

It sounds obvious. It's also the single biggest difference between a query that comes back in two seconds and one that times out.

## Time windows with `let`

Naming the windows makes a query readable months later, and makes it easy to change "the last day" to "the last week" in one place:

```kql
let lookback = 14d;
let recent = 1d;
SigninLogs
| where TimeGenerated > ago(lookback)
| extend Period = iff(TimeGenerated > ago(recent), "recent", "baseline")
| summarize Signins = count() by UserPrincipalName, Period
```

## "First time we've seen this" with `leftanti`

The most useful join I know. Build a baseline of what's normal, then keep only the recent rows that don't match it. Here, successful sign-ins from a country the user hasn't signed in from in the last two weeks:

```kql
let lookback = 14d;
let recent = 1d;
let known = SigninLogs
    | where TimeGenerated between (ago(lookback) .. ago(recent))
    | where ResultType == "0"
    | summarize by UserPrincipalName, Country = tostring(LocationDetails.countryOrRegion);
SigninLogs
| where TimeGenerated > ago(recent)
| where ResultType == "0"
| extend Country = tostring(LocationDetails.countryOrRegion)
| join kind=leftanti known on UserPrincipalName, Country
| project TimeGenerated, UserPrincipalName, Country, IPAddress, AppDisplayName
```

Swap the columns and the same pattern finds a first-time process on a server, a first-time admin tool, or a first-time destination port.

## Parsing JSON without fighting it

A lot of useful fields are buried in dynamic columns. Two tools do most of the work: `tostring()` to pull a value out, and `mv-expand` to turn an array into rows.

Inbox rules that forward mail outside are a classic sign of a compromised mailbox:

```kql
OfficeActivity
| where TimeGenerated > ago(7d)
| where Operation in ("New-InboxRule", "Set-InboxRule")
| mv-expand Parameter = todynamic(Parameters)
| where tostring(Parameter.Name) in ("ForwardTo", "RedirectTo", "ForwardAsAttachmentTo")
| project TimeGenerated, UserId, Operation, ForwardingTarget = tostring(Parameter.Value), ClientIP
```

And role assignments, because a new Global Administrator should never be a surprise:

```kql
AuditLogs
| where TimeGenerated > ago(7d)
| where OperationName == "Add member to role"
| extend Actor = tostring(InitiatedBy.user.userPrincipalName)
| extend Target = tostring(TargetResources[0].userPrincipalName)
| extend Role = tostring(TargetResources[0].modifiedProperties[1].newValue)
| project TimeGenerated, Actor, Target, Role
```

The array index on `modifiedProperties` can shift between log versions. Before trusting it, run the query once with `| project TargetResources` and look at the JSON yourself.

## Spikes, not thresholds

Fixed thresholds break the moment the business changes. `make-series` with `series_decompose_anomalies` compares each hour to the pattern around it instead:

```kql
SigninLogs
| where TimeGenerated > ago(14d)
| where ResultType != "0"
| make-series Failures = count() default = 0 on TimeGenerated from ago(14d) to now() step 1h
| extend (Anomalies, Score, Baseline) = series_decompose_anomalies(Failures, 2.5)
| mv-expand TimeGenerated to typeof(datetime), Failures to typeof(long), Anomalies to typeof(int)
| where Anomalies == 1
| project TimeGenerated, Failures
```

Pipe the series into `render timechart` while you're exploring. Seeing the shape of the data beats reading numbers.

## Rare things on endpoints

A file hash seen on exactly one device, for the first time today. Not malicious by itself, but a good place to start looking:

```kql
DeviceProcessEvents
| where Timestamp > ago(30d)
| summarize Devices = dcount(DeviceName), FirstSeen = min(Timestamp) by SHA256, FileName
| where Devices == 1 and FirstSeen > ago(1d)
| order by FirstSeen desc
```

## Turning a hunt into a rule

A hunt that found something once is worth turning into a scheduled analytics rule. Before I would, I'd check:

1. **Does it run fast?** Analytics rules have limits; trim columns and time ranges.
2. **Are the entities mapped?** Account, host and IP at minimum, so incidents correlate.
3. **What does a week of results look like?** Run it over the last 7 days. If it would have fired 300 times, it's a hunting query, not a rule.
4. **Is there an exclusion list?** Put known-good accounts or IPs in a watchlist rather than hard-coding them.
5. **Would the analyst who gets this at 3am understand it?** Write the description for them, not for yourself.

That last one matters more than it sounds. A rule nobody understands gets closed as noise.
